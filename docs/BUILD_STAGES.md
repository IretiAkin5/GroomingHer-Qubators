# GroomingHer rebuild: stages and review routes

6 October 2026. This implementation follows the four founder-supplied documents. Those are product/design requirements, not a declaration that their live services or approvals exist. The user's initial-build instruction governs this delivery: fictional demonstration only, no real children’s health collection.

## Stage 1 — documents and public website

The founder README, PRD 3.1, implementation plan and design plan were read before source changes. The canonical plans are installed in the root; PRD.md and IMPLEMENTATION_PLAN.md mirror their canonical versions. Supporting design, research, architecture and user-story documents now match the approved education-first scope. Superseded Word files and the former backend are labelled in docs/archive, outside the active application; earlier static HTML previews point to the current app and docs.

Preview routes: `/`, `/about`, `/solutions/girls`, `/solutions/parents`, `/solutions/schools`, `/how-it-works`, `/resources`, `/contact`, `/get-started`, `/login`. Policies, FAQs, child-safety, accessibility, recovery and support are available without an account.

The landing page follows the specified section order and uses the PRD 3.1 supplied preview copy. The design plan's earlier “copy to be added” instructions are superseded by that supplied copy. No placeholders are used on functional screens. Palette and original SVG illustrations are proposed for founder review, not claimed approved branding.

Completed browser checks: desktop Solutions navigation, mobile menu, resource filters/detail, demo enquiry preview and failure. Desktop and phone screenshots are generated by the journey suite.

## Stage 2 — fictional joining and role spaces

Get Started opens role selection. Girl and Parent choices open brief fictional onboarding; School opens interest registration, with a separate fictional staff-invitation preview. `/onboarding/girl`, `/onboarding/parent`, `/onboarding/school` demonstrate invitations, minimal role questions, skippable learning/access preferences, separate permissions and intended connection confirmation. Invalid/withdrawn invitations, outside-age, caregiver authority, pending-permission and wrong-pairing states block progression to the demo until corrected. Optional preferences can resume in this browser tab. No personal names, invitation codes or medical histories can be entered.

Use `/login` to enter a fixed fictional identity directly for product review. It is explicitly demo access, not authentication. Each role has its own visible navigation. A client guard blocks another role's direct route; this demonstrates the UI boundary only, not production server authorisation. No actual private data exists.

| Role | Preview journeys |
| --- | --- |
| Girl | `/demo/girl`: learning-first home; six lessons with reflections/fictional checks; resources; learning-only progress; optional fixed-fictional diary save/edit/delete/cancel; exact-text chosen-sharing preview, confirmation, cancellation and failure; shared messages; support; sharing pause and exit. |
| Parent | `/demo/parent`: practical guides and conversation starters; distinct Christian reflection; only confirmed recipient messages; six-week programme; support; separate permission/connection explanation; no diary, private questions or health scores. |
| School | `/demo/school`: outstanding readiness checklist; six session draft dates; sample materials/print pack; fictional joining and attendance corrections; physical-question-box guidance; combined feedback with small-group suppression; named-staff boundary/withdrawal simulation. |

Recommended review: choose a Girl identity → explore a lesson → skip a check → skip the diary → optionally try/edit/delete a fictional entry → cancel sharing → preview delivery failure → confirm a sample message → open the offered recipient preview. The parent sees the exact confirmed message with no diary attachment. Support is always independent of the diary and AI.

School review: inspect “Not ready” → change a fictional session date → use the Public website link and Log In to switch to Parent without refreshing → view the draft schedule. Any full refresh resets these memory-only drafts. Attendance corrections have no health reasons. Feedback with fewer than five sample responses is withheld; a live suppression threshold requires privacy review.

## Stage 3 — checks and reusable development

From `app`:

```bash
npm ci
npm run dev -- --hostname 0.0.0.0
```

For production validation, stop development before `npm run build`, then run `npm run start -- --hostname 0.0.0.0`. Node 24.19.0 is validated; no database or service credentials are needed. Optional Docker Compose now runs only the demo web app; the Docker image build remains unverified. Netlify publication and live route checks were verified on 7 October 2026, as recorded in `VALIDATION.md`.

Browser checks use `npm run test:e2e` with the app running. They choose `/usr/bin/chromium` when available or Playwright's installed browser. On a fresh machine use `npx playwright install --with-deps chromium`. `CHROMIUM_PATH` and `TEST_BASE_URL` can override those defaults; `GROOMINGHER_ARTIFACTS` sets the screenshot/PDF directory. GitHub Actions runs the same production checks, but its remote execution is not yet verified.

The suite checks public and legacy routes, blocked collection APIs, desktop/phone navigation, onboarding blockers/resume, fictional diary CRUD, sharing confirmation/cancellation/failure, recipient visibility, learning/progress, disabled AI/human-help routes, staff readiness/schedules/attendance, small-group results, logout/revocation, horizontal overflow and automated WCAG A/AA checks. It generates screenshots and a print-to-PDF sample pack. Automated accessibility checks do not constitute an accessibility certification or replace manual/user testing.

## Explicit demonstration boundaries

- `/api/health` reports `mode: fictional-demo` and `healthCollection: false`. All other API paths return HTTP 410 for read/write methods without reading the request body. Earlier public profile/symptom/triage/sharing endpoints are disabled.
- All identities and details are fictional. Forms have fixed examples and controlled choices; no health free text or real credentials are accepted. No diary, contact, school-interest, report or message is sent to a server. No external analytics are installed.
- Only the role marker and fixed onboarding preferences are tab-scoped session storage. Demo diary/messages/progress and schedule drafts are memory-only; refresh clears them and exit clears the role marker/preferences too. Entering another demo role clears prior diary/messages/progress. The explicit girl-to-recipient preview carries only her confirmed sample messages and clears diary/progress.
- AI is intentionally unavailable. There is no Groq call, diary access or generated explanation from unreviewed content. Fixed example buttons demonstrate lesson, diagnosis-limit and human-support routes without inviting personal questions.
- Every health sample and print pack states “awaiting professional review”, version/date and no approval. Christian reflections are separate and also await review. School contacts are explicitly fictional, never live phone numbers or verified service hours.
- The planned pilot remains unconfirmed and not ready. No school, funding, professional reviewer or operational support is invented.
